## 途中で「参加者が退出しました」になる問題への、フロント側の対策 — 2026-11-09 14:40 JST（担当: フロント）

ゲームのルール・API・Firestore の約束の変更はなし。

**原因（調べた結果）**: 本物のサーバーで、ゲームの途中に API が `503 Service Unavailable` を返し、生存確認も弾かれて15秒途絶え、退出あつかいになっていた。API の起動設定（`backend_a/entrypoint.py`）の uvicorn `limit_concurrency=8` が、同時に8件を超えた要求に即座に 503 を返すため（生存確認を10件同時に送ると2件が0.08秒で 503。1件ずつなら全部成功）。生存確認1回の処理も0.7〜2.7秒かかる。サーバーの変更は A の担当なので、フロントでは変えていない。

| 内容 | 理由 |
|---|---|
| 生存確認の1回が返事のないまま止まっても、4.5秒で待つのをやめて次を送る。本物のサーバーへの通信は4秒で打ち切る（`src/game/heartbeat.ts`、`src/api/real/realBackend.ts`） | 前の送信が終わるまで次を送らない作りだったため、1回固まると生存確認がずっと止まっていた |
| 生存確認に失敗したら、5秒を待たずに1.5秒後に1回送り直す | 503 にぶつかっても、15秒の間に何度か試せるようにするため |
| 画面が表に戻ったとき・通信がつながり直したときに、すぐ生存確認を送る | 戻った瞬間に、生きていることを伝えるため |
| 人Bの座標のまとまりを、1つずつ送る（前の送信が終わるまで座標をためておく）（`src/screens/GestureScreen.tsx`） | サーバーに同時に届く要求を減らし、503 を起こしにくくするため |
| 画面を消さない設定（Wake Lock）を、ゲーム中だけでなくロビーでも使い、端末が解除したとき・画面を触ったときに取り直す（`src/lib/hooks.ts`） | 待っている間は誰も触らないので画面が消え、ページが止まって退出あつかいになるため |
| ロビーに「ゲームが終わるまでページを開いたまま、画面を消したりアプリを切り替えたりしない」の注意を出す | 画面が消えるとフロントだけでは防げないため |

- テスト: 生存確認が固まったとき・古い送信が後から終わったとき・画面が戻ったとき・失敗したときのテストを足した（全36件）。lint・型チェック・ビルドは成功。
- **未確認**: 本物のサーバーでの1周（最後の確認では、サーバーの開始と AI の絵が極端に遅くなり、終わらなかった）、iPhone での Wake Lock の効き。
- A へのお願い（根本の対策）: `limit_concurrency=8` を上げるか外す（Cloud Run の concurrency 8・最大2台と二重に絞っている）、生存確認ごとの後片付け（ジョブの回復・outbox の送信・掃除）を軽くするか別にする、退出の判定（15秒）を長くする。
- 2026-11-09 16:50 A のレビュー（PR #15）を受けて直した: 生存確認の送り直しは、ふつうの送信1回につき最大1回にし、送り直しの失敗では次を予約しない（連続503で送信が増えないように）。ふつうの送信（間隔・画面の復帰）を始めるときは古い予約を取り消し、待つのをあきらめた古い回の失敗では予約しない。人Bの座標は `src/gesture/batchSender.ts` に分け、1回の送信を 200,000 バイト以内（API の上限 250,000 バイトに余裕）に切って順に送る。録画の終了後は座標の送信を最大1秒しか待たず、録画のアップロードと終了通知に受付時間（締切＋猶予5秒）を残す。テストを足した（連続503・古い予約・画面の復帰・古い回の失敗、両手30秒分の分割、返事が遅い・返らないときの打ち切り。全47件）。
- 2026-11-09 16:50 A の #16（生存確認から保守処理を外した）の配備後に、検証用URL（この PR と main を合わせたもの、本物の API）で3人1周を試した。録画が始まった直後から約12秒、生存確認・座標・録画のアップロードが続けて 503 になり、結果まで進まなかった（1周で 503 が54件、生存確認の成功16件）。録画の前は 503 なし。
